### [2026-07-18] [coder-sonnet] — FIX-001 Panel-Ops dashboard: el() null-attribute bug
**Decisión de código:** En `proyectos/panel-ops/tools/roadmap-dashboard/index.html`, el helper `el(tag, attrs, children)` (~línea 205) hacía `node.setAttribute(k, v)` incondicionalmente para cualquier atributo, incluidos `null`/`undefined`/`false`. Como `disabled` es un atributo booleano HTML, su sola presencia (aunque el valor fuera el string `"null"`) desactivaba el botón. Se agregó un guard antes del `setAttribute` genérico: `else if (v === null || v === undefined || v === false) continue;`. Una sola línea, sin refactor adicional (fuera de alcance por ticket).
**Trampa evitada:** Al auditar el resto del archivo por otros usos de atributos booleanos (`checked`, `readonly`, etc.) que pudieran depender del comportamiento roto, solo se encontró un sitio (`disabled` en el botón Ejecutar de cada card). Los usos de `value: ''` (placeholder de modelo codex, input de autor de comentario) no se ven afectados porque `''` no es `null`/`undefined`/`false`.
**Patrón reusable:** Verificación sin reiniciar servidor (index.html se sirve por request) — usar `curl -s http://127.0.0.1:PORT/` para confirmar el parche está servido, y `curl -s .../api/tickets` para verificar estado real de tickets (`rawState`, `hasActiveRun`) contra la lógica esperada del botón. Ver `proyectos/panel-ops/tools/roadmap-dashboard/index.html:205-215` y `proyectos/panel-ops/roadmap-status.md` (entrada FIX-001) y `proyectos/panel-ops/comments/FIX-001.jsonl` para evidencia completa.

### [2026-07-17] [coder-sonnet] — FIX-002 Panel-Ops: claude runner bloqueado por sandbox de permisos interactivo
**Decisión de código:** En `proyectos/panel-ops/tools/roadmap-dashboard/server.mjs`, función `launchExecution()` (~línea 385-410), el spawn del runner `claude` (~línea 398-406) no incluía ningún flag de permisos no-interactivo, por lo que cada tool call Write/Edit del subproceso `claude` lanzado en background era rechazado con "you haven't granted it yet" (sin aprobador interactivo disponible). Se agregaron dos elementos literales al array de args del spawn: `'--permission-mode', 'acceptEdits'` — solo en la rama del runner `claude`, la rama `codex` queda intacta. Se mantuvo `spawn()` como array de argumentos con `shell: false` (sin interpolación de shell). Explícitamente NO se usó `--dangerously-skip-permissions` (ese flag también habilita Bash sin restricción, fuera del alcance del ticket FIX-002).
**Trampa evitada:** A diferencia de lo que sugería el fallback genérico del dashboard ("blocked... no terminal state"), el log viejo (`logs/INF-001-2026-07-18T03-30-00-012Z.log`) sí mostraba evidencia real de rechazo de Write — no había que reinventar el diagnóstico, solo confirmar contra ese log de referencia. Después del parche, `server.mjs` requiere reinicio del proceso Node para tomar efecto (a diferencia de `index.html`, que se sirve por request) — hay que matar el proceso viejo en el puerto 4570 (`lsof -nP -iTCP:4570 -sTCP:LISTEN`) y relanzar antes de cualquier prueba funcional, si no el fix parece "no funcionar" aunque el archivo esté bien parchado.
**Patrón reusable:** Para verificar que `acceptEdits` funciona de verdad (no solo que el flag está en el array), inspeccionar el JSONL de `stream-json` del log de ejecución buscando eventos `tool_use` con `name` en `Write`/`Edit` y su `tool_result` correspondiente por `tool_use_id` — un resultado tipo "File created successfully at: ..." (y el archivo presente en disco) es prueba positiva; una cadena "you haven't granted it yet" es prueba negativa. Ojo: `acceptEdits` NO cubre `Bash` — es normal y esperado ver `tool_result` con `is_error:true` del tipo "sed command requires approval (contains potentially dangerous operations)" en el mismo log; no confundir con fallo del fix. Ver `proyectos/panel-ops/tools/roadmap-dashboard/server.mjs:398-411`, `proyectos/panel-ops/roadmap-status.md` (entrada FIX-002) y `proyectos/panel-ops/comments/FIX-002.jsonl` para evidencia completa, incluyendo el log de comparación pre/post fix.
